# Scaffold and initial infrastructure

This is the **first issue** — it establishes the project foundation before any use case (UC-01 … UC-37) is implemented. Every subsequent use case depends on this scaffold.

## Scope

Set up the Rust **Cargo workspace** with the three crates defined in the [Operations & Infrastructure Document §2.3](docs/requirements/Operations%20%26%20Infrastructure%20Document.md#23-repository-layout):

- `crates/alexandria-core` — domain logic (Command/Query handlers, repository traits + sqlx impl, auth service)
- `crates/alexandria-http` — axum REST/JSON server surface
- `crates/alexandria-ffi` — C ABI surface generated by `cbindgen`

## Acceptance criteria

- [ ] `cargo build --workspace` succeeds with `#![deny(unsafe_code)]` enforced in every crate.
- [ ] `cargo test --workspace` passes (initial smoke tests only).
- [ ] Repository layout matches the Operations & Infrastructure Document §2.3.
- [ ] `alexandria-core` exposes repository and auth-service **traits**, an `errors.rs` with `thiserror` domain errors, and a `migrations/` directory for `sqlx migrate` (empty or with the initial migration).
- [ ] `alexandria-http` boots an axum server bound to a loopback address, with auth + logging + error-mapping middleware stubs and a `GET /health` endpoint returning the contract in [Operations & Infrastructure Document §5.2](docs/requirements/Operations%20%26%20Infrastructure%20Document.md#52-response-contract).
- [ ] `alexandria-ffi` has a `build.rs` running `cbindgen` and an `extern "C"` smoke surface.
- [ ] `config.toml.example` documents every key in [Operations & Infrastructure Document §3](docs/requirements/Operations%20%26%20Infrastructure%20Document.md#3-configuration) with `ALEXANDRIA_*` env overrides.
- [ ] Structured logging is set up via `tracing` / `tracing-subscriber`.
- [ ] The README's use-case progress table renders and reports this issue as the only one in progress.
